## Status

Accepted (documents the convention established by ADR-0001 / DESIGN-0010 and
account-scoped by IMPL-0015; adds the executable key-template assertions)

## Context

Cross-module composition in this fleet flows exclusively through S3-backed
remote state (ADR-0001): 12 `data.terraform_remote_state` blocks across 10
consumer modules read the outputs of producer stacks. Every one of those
reads **composes its S3 key from a hardcoded template** — e.g.
`rds/proxy` reads
`${account_name}/${region}/rds/${dir}/${target_identifier}/terraform.tfstate`
where `dir` comes from a `target_dir_map` local — but **no producer module
sets or can verify its own key**. In production the producer's state key is
generated by the Terragrunt live repo's folder layout
(`path_relative_to_include()`-style), which lives in a different repository.

The contract therefore has three legs, only two of which are visible to this
repo:

1. The consumer's hardcoded key template (this repo).
2. The test fixtures that seed stub state at the same keys (this repo).
3. The live repo's directory naming, which determines where producer state
   actually lands (NOT this repo).

Until this ADR, the convention existed only in prose (DESIGN-0010
"Composition via remote state", scattered variable descriptions) and in
duplicated string literals. Nothing pinned the templates as an executable
contract: the plan suites stub the data sources wholesale via
`override_data` (the key is never evaluated), and the Pro apply fixtures
seed the same convention they read — self-consistent by construction, so
they can confirm the read *mechanics* but never catch template drift.

The failure mode when a producer is deployed at an unexpected path is loud
but unhelpful: `terraform plan` on the consumer fails with `Unable to find
remote state — No stored state was found for the given workspace in the
given backend`, naming neither the bucket nor the composed key (probed
against LocalStack, 2026-07-29).

## Decision

### The canonical key shape

Every cross-module state read/publish uses the account-scoped key
(IMPL-0015):

```text
<account_name>/<region>/<shape>/<name>/terraform.tfstate
```

- `<account_name>` — the Terragrunt account name (e.g. `platform-dev`).
- `<region>` — the deployment region of the producer stack.
- `<shape>` — the producer's service path segment(s): `vpc`, `eks`,
  `rds/instance`, `rds/cluster`, `rds/serverless`.
- `<name>` — the producer instance's stable identifier (see coupling below).

In the live repo this means the producer stack's directory **must** be
`<account_name>/<region>/<shape>/<name>/` — the folder path IS the key.
Renaming a live-repo folder silently moves the state key and breaks every
consumer read at plan time.

### The contract table

| Consumer module | Read | Key template | Producer (must live at that path) |
|---|---|---|---|
| `eks/cluster` | vpc | `<acct>/<region>/vpc/<vpc_name>/…` | `network/vpc-lookup` (or future `network/vpc`) |
| `eks/managed-node-group` | eks + vpc | `<acct>/<region>/eks/<cluster_name>/…`, `<acct>/<region>/vpc/<vpc_name>/…` | `eks/cluster`, `network/vpc-lookup` |
| `eks/addons` | eks | `<acct>/<region>/eks/<cluster_name>/…` | `eks/cluster` |
| `eks/pod-identity-access` | eks | `<acct>/<region>/eks/<cluster_name>/…` | `eks/cluster` |
| `rds/serverless` | vpc | `<acct>/<region>/vpc/<vpc_name>/…` | `network/vpc-lookup` |
| `rds/cluster` | vpc | `<acct>/<region>/vpc/<vpc_name>/…` | `network/vpc-lookup` |
| `rds/instance` | vpc | `<acct>/<region>/vpc/<vpc_name>/…` | `network/vpc-lookup` |
| `rds/proxy` | target | `<acct>/<region>/rds/<dir>/<target_identifier>/…` — `dir` = `target_dir_map[target_type]`: `rds-instance`→`instance`, `aurora-cluster`→`cluster`, `serverless`→`serverless` | `rds/instance` \| `rds/cluster` \| `rds/serverless` |
| `rds/read-replica` | cluster | `<acct>/<region>/rds/cluster/<cluster_identifier>/…` | `rds/cluster` |
| `efs/filesystem` | vpc + eks | `<acct>/<region>/vpc/<vpc_name>/…`, `<acct>/<region>/eks/<cluster_name>/…` | `network/vpc-lookup`, `eks/cluster` |

All 12 reads carry the cross-account `assume_role`
(`arn:aws:iam::<account_id>:role/<deploy_role_name>`,
`session_name = "Deploy-Tf"`) and `region = <remote_state_bucket_region>`
per IMPL-0015.

### The identifier coupling

`<name>` is not free-form — it is the same string in three places:

- **RDS targets:** the DB module's `identifier_prefix` == the live-repo
  folder name == the consumer's `target_identifier` (proxy) /
  `cluster_identifier` (read-replica). The proxy additionally registers that
  string as the `db_instance_identifier` / `db_cluster_identifier` on the
  proxy target group, so a mismatch that somehow survived the state read
  would still fail at the RDS API.
- **EKS:** the cluster module's `cluster_name` == the folder name == every
  EKS consumer's `cluster_name`.
- **VPC:** the `vpc_name` used by `network/vpc-lookup`'s state placement ==
  every VPC consumer's `vpc_name`.

### Enforcement — what is checked where

| Leg | Enforced by |
|---|---|
| Consumer key template + `target_dir_map` | **Key-template plan assertions** (this ADR): each consumer's plan suite asserts `data.terraform_remote_state.<name>.config.key` composes to the exact expected string for known inputs. Any edit to a template or the map fails `just tf test` / the CI plan tier. |
| Read mechanics (S3 + assume_role + key round-trip) | The LocalStack apply suites — fixtures seed state at the contract key, consumers read it back. |
| State *content* after a successful read | Consumer preconditions (`rds/proxy` V2–V5, `rds/read-replica` stale-state check, etc.). |
| Live-repo folder naming | **Cannot be enforced from this repo.** The live repo must carry its own check that stack directories match `<account_name>/<region>/<shape>/<name>`. Until then, the failure mode is a loud-but-vague consumer plan error (`Unable to find remote state`). |

Each affected module's `README.md` carries a "Remote-state key contract"
section naming its exact reads and couplings, pointing here.

## Consequences

### Positive

- The convention is documented once, authoritatively, instead of living in
  scattered variable descriptions and duplicated literals.
- Template drift inside this repo (editing a key string, changing
  `target_dir_map`, a new module inventing its own shape) now fails CI via
  the plan assertions instead of surfacing as a broken deploy.
- Operators debugging `Unable to find remote state` have a contract table
  to diff against.

### Negative

- The live-repo leg remains unenforced from here — the ADR makes the gap
  explicit rather than closing it. Closing it requires a naming check in
  the live repository.
- One more assertion per plan suite to keep in sync if the contract ever
  changes deliberately (a fleet-wide, coordinated edit by design).

### Neutral

- The assertions pin `config.key` under `override_data` — the stub replaces
  the data source's *outputs*, while `config` remains the configured input,
  so no live S3 is needed.

## Alternatives Considered

- **A shared "key composition" module** (one `locals` factory emitting keys
  for every consumer): rejected — a module call per data source adds
  indirection the Gruntwork-style pattern deliberately avoids, and the
  templates differ by exactly one segment; the assertions give the same
  drift protection without restructuring 12 reads.
- **Producer-side validation of its own key**: impossible — a Terraform
  module cannot introspect its backend configuration at plan/apply time;
  the key belongs to Terragrunt.
- **Verifying the live repo from this repo's CI**: rejected — cross-repo
  checkout coupling in CI for a repo this one does not control; the check
  belongs in the live repo itself.
