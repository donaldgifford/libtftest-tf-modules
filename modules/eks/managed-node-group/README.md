# managed-node-group

EKS managed node group for the platform workload classes — optional gVisor
sandboxing, minimal node IAM, IMDSv2 + hop-limit 2, and ARM64/Graviton as the
default architecture.

- Terraform interface: [USAGE.md](./USAGE.md) (generated by `terraform-docs`)
- Design:
  [`docs/design/0001-secure-eks-managed-node-group-with-gvisor.md`](../../../docs/design/0001-secure-eks-managed-node-group-with-gvisor.md),

## Workload classes

`var.workload_class` selects the platform class this group serves (the taxonomy
is the platform's, not this module's — new classes are deliberate one-line enum
additions here, never free-form caller strings). One input drives three things:
the `workload-class` label, the matching `NO_SCHEDULE` taint, and the gVisor
default.

| `workload_class` | `workload-class` label | `<class>:NO_SCHEDULE` taint | gVisor default |
| ---------------- | ---------------------- | --------------------------- | -------------- |
| `core` (default) | yes                    | **no** — untainted          | off            |
| `observability`  | yes                    | yes                         | off            |
| `analytics`      | yes                    | yes                         | off            |
| `temporal`       | yes                    | yes                         | off            |
| `secure`         | yes                    | yes                         | **on**         |

`core` is the untainted landing zone by design: the platform baseline (ArgoCD,
External Secrets, the AWS Load Balancer Controller) tolerates nothing, so a
taint there means nothing schedules. Every other class is opt-in via a matching
toleration.

`var.gvisor_enabled` overrides the gVisor default in either direction (`null`
default = follow the class). The **`runtime=gvisor` label and the gVisor install
ride the effective value, not the class** — a sandboxed `analytics` pool
advertises the runtime, and a `secure` pool with gVisor overridden off must not
claim a sandbox it does not have.

> [!WARNING]
> **Default-behavior change (DESIGN-0024 / IMPL-0020).** Before this change the
> module hardwired the `secure` class: every node was born
> `workload-class=secure:NO_SCHEDULE` with gVisor installed. The default is now
> `core` — untainted and gVisor-less. A default invocation is **not** the old
> posture. Callers wanting it set `workload_class = "secure"` explicitly. The
> change was taken deliberately while the module had zero live consumers
> (INV-0011 OQ 13); the `secure` posture stays pinned byte-for-byte by the
> explicit-secure runs in `tests/workload_class.tftest.hcl` and
> `tests/user_data.tftest.hcl`.

### Reserved label keys

`additional_labels` merges on top of the class-derived labels and wins on
collision, but it reaches the **EKS API label path only** — the kubelet
`--node-labels` fragment in user data is composed from the class rules alone.
Overriding a module-managed key would therefore make a node advertise something
its bootstrap never applied. `runtime=gvisor` on a node with no `runsc` is
exactly the lie the effective-gVisor rule exists to prevent, so three keys are
reserved and rejected at plan:

| Reserved key | Set instead by |
|---|---|
| `workload-class` | `var.workload_class` |
| `runtime` | the effective gVisor value (`var.gvisor_enabled` or the class rule) |
| `kubernetes.io/arch` | `var.architecture` |

`additional_taints` has no such restriction: taints layer alongside the class
taint rather than replacing it, so there is nothing to forge.

## Out-of-band: the gVisor `RuntimeClass`

This module **does not** create the gVisor `RuntimeClass`. Per
[ADR-0011](../../../docs/adr/0011-runtimeclass-delivered-out-of-band-not-by-terraform.md),
Terraform modules in this repo manage AWS API resources only; Kubernetes-API
objects are delivered out-of-band.

Workloads in this node group opt into gVisor by setting
`spec.runtimeClassName: gvisor`. That reference resolves only if a
cluster-scoped `RuntimeClass` named `gvisor` exists. The manifest is the same in
every cluster — one per cluster, regardless of how many secure node-group
instantiations (`arm64` + `amd64`) the cluster runs.

### The manifest

```yaml
# gvisor-runtimeclass.yaml
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: gvisor
handler: runsc
scheduling:
  nodeSelector:
    workload-class: secure
    runtime: gvisor
  tolerations:
    - key: workload-class
      value: secure
      operator: Equal
      effect: NoSchedule
```

The values are stable constants matching what this module applies **for a
`secure` group** (or any group with `gvisor_enabled = true` — adjust the
`workload-class` selector and toleration to that group's class):

| Field                     | Value                                     | Where it comes from                                             |
| ------------------------- | ----------------------------------------- | --------------------------------------------------------------- |
| `handler`                 | `runsc`                                   | containerd handler registered by user data (ADR-0005, ADR-0008) |
| `scheduling.nodeSelector` | `workload-class=secure`, `runtime=gvisor` | `aws_eks_node_group.labels`                                     |
| `scheduling.tolerations`  | `workload-class=secure:NoSchedule`        | `aws_eks_node_group.taint`                                      |

### Option A — Apply via `kubectl`

For homelab / dev clusters and environments without a GitOps tool:

```sh
aws eks update-kubeconfig --region "$AWS_REGION" --name "$CLUSTER_NAME"
kubectl apply -f gvisor-runtimeclass.yaml
```

Verify:

```sh
kubectl get runtimeclass gvisor -o yaml
```

Run this once per cluster after the cluster + node-group Terraform applies have
completed and at least one secure node is `Ready`.

### Option B — Apply via Argo CD + Kustomize

Recommended for production. The manifest lives in a GitOps repository under a
per-cluster overlay; Argo syncs it like every other cluster-scoped object.

Layout (consumer's GitOps repo):

```
clusters/<env>/<cluster-name>/
├── base/
│   └── gvisor-runtimeclass/
│       ├── kustomization.yaml
│       └── runtimeclass.yaml
└── overlays/
    └── <cluster-name>/
        └── kustomization.yaml
```

**`base/gvisor-runtimeclass/runtimeclass.yaml`** — the manifest above, verbatim.

**`base/gvisor-runtimeclass/kustomization.yaml`**:

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - runtimeclass.yaml
```

**`overlays/<cluster-name>/kustomization.yaml`**:

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base/gvisor-runtimeclass
```

**Argo `Application`** (in the Argo control-plane cluster):

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: <cluster-name>-gvisor-runtimeclass
  namespace: argocd
spec:
  project: cluster-bootstrap
  source:
    repoURL: https://github.com/<org>/<gitops-repo>.git
    targetRevision: main
    path: clusters/<env>/<cluster-name>/overlays/<cluster-name>
  destination:
    server: https://<cluster-api-endpoint>
    # namespace omitted — RuntimeClass is cluster-scoped
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=false
      - ServerSideApply=true
```

Add the `gvisor-runtimeclass` Application to the same Argo sync wave as other
cluster-bootstrap manifests (NetworkPolicies, admission webhooks, etc.). It
should sync after the node-group Terraform apply has completed.

## Workload opt-in (consumer reference)

Once the `RuntimeClass` exists, workloads opt in:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: secure-app
spec:
  template:
    spec:
      runtimeClassName: gvisor
      # nodeSelector + toleration are injected by RuntimeClass.scheduling
      # Add kubernetes.io/arch only if the workload targets a specific arch
      # and its container image is single-arch:
      # nodeSelector:
      #   kubernetes.io/arch: arm64
      containers:
        - name: app
          image: <multi-arch-image>:<tag>
```

Multi-arch container images schedule on either architecture in mixed-arch
clusters without an arch nodeSelector.

## Per-architecture instantiation

This module is single-arch per instantiation (ADR-0006). To run both `arm64` and
`amd64` secure node groups on the same cluster, instantiate twice with
different `var.architecture` and `var.nodegroup_name`.

```hcl
module "node_group_arm64" {
  source = "../../modules/eks/managed-node-group"

  remote_state_bucket = var.remote_state_bucket
  region              = var.region
  cluster_name        = var.cluster_name
  vpc_name            = var.vpc_name
  nodegroup_name      = "secure-arm64"

  # architecture defaults to the arm64 shape; explicit for clarity:
  architecture = {
    name                   = "arm64"
    ami_type               = "AL2023_ARM_64_STANDARD"
    gvisor_arch            = "aarch64"
    k8s_arch               = "arm64"
    default_instance_types = ["m7g.large", "m7g.xlarge", "c7g.large", "c7g.xlarge"]
  }
}

module "node_group_amd64" {
  source = "../../modules/eks/managed-node-group"

  remote_state_bucket = var.remote_state_bucket
  region              = var.region
  cluster_name        = var.cluster_name
  vpc_name            = var.vpc_name
  nodegroup_name      = "secure-amd64"

  architecture = {
    name                   = "amd64"
    ami_type               = "AL2023_x86_64_STANDARD"
    gvisor_arch            = "x86_64"
    k8s_arch               = "amd64"
    default_instance_types = ["m7i.large", "m7i.xlarge", "c7i.large", "c7i.xlarge"]
  }
}
```

The Boilerplate-generated Terragrunt config (DESIGN-0001) computes the
arch-derived fields from a single `architecture = "arm64"` choice and passes
the fully-formed object in.

## Wiring the optional ECR pull-through cache policy

Per ADR-0015, the ECR pull-through cache module emits a managed-style IAM
policy ARN that consumers opt into by passing it through
`var.extra_node_policies`. **Two stages of consent**: instantiating the cache
module emits the policy; passing the ARN here attaches it. Either alone is a
no-op.

```hcl
module "node_group" {
  source = "../../modules/eks/managed-node-group"
  # ...

  extra_node_policies = [
    module.ecr_pull_through_cache.node_pull_through_policy_arn,
  ]

  containerd_pull_through_mirror = {
    enabled          = true
    cache_url_prefix = module.ecr_pull_through_cache.cache_url_prefixes["docker-hub"]
    upstreams = [
      { host = "registry-1.docker.io", prefix = "docker-hub" },
    ]
  }
}
```

The `containerd_pull_through_mirror` block is separately opt-in per
IMPL-0005 Q8 — independent from the IAM gate so callers can attach the
policy without redirecting runtime traffic (e.g., during validation).

## Remote-state key contract (ADR-0020)

This module **reads** two producer states:

```text
<account_name>/<region>/eks/<cluster_name>/terraform.tfstate
<account_name>/<region>/vpc/<vpc_name>/terraform.tfstate
```

`cluster_name` / `vpc_name` must equal the producer stacks' live-repo
folder names. A mismatch fails this module's plan with `Unable to find
remote state` (the error names neither bucket nor key — diff against this
contract). Both key templates are pinned by plan assertions in
`tests/default.tftest.hcl`; see ADR-0020 for the fleet table.
